## Active user path

The current Web and Windows reviewer both run apps/viewer as a read-only product. Source catalog import/representative-date selection is not exposed in that UI. tools/gis/territorial-library.js retains the source calculation contract: exact date selection does not fall back; explicit representative imports create a static project instance with unbounded project binding and preserve sourceReferenceDate, sourceGeometryValidity and historicalProvenance. This is a tool API, not an existing user-visible import dialog.

The active project-file reader admits only .gpkg through the production read worker and projectDomain.open. There is no current production GeoPackage writer in the Viewer graph: the writer reached by tests/helpers/production-geopackage.mjs is retained compatibility-fixture source. It must not be promoted into a user export path. apps/editor/AGENTS.md also explicitly prohibits reactivating GeoPackage writes in the Windows reviewer. A generated .gpkg reference-project route was an initial candidate, but is therefore not selected as the minimal product implementation.

The separate builtinMonthClock retains its committed month while a file is open; however the current builtinMapBtn invokes followNow(), so that button returns to the current month, not the previous month. The earlier draft statement that the existing return action preserves the original month was incorrect. The explicit reference workflow needs its own guarded restore through the existing clock owner, without changing ordinary file-open/builtin-return behavior.

Recommended minimum: an explicit read-only reference-date view, using the already-published compiled country files and exact date bindings. The user deliberately chooses 1914-07-28 (Austria-Hungary and Serbia) or 1914-07-31 (Germany). This view shows a persistent source-date/provisional notice and explains that it is a fixed reference snapshot, not the month-end world's historical coverage. The ordinary monthly selector continues to mean month end. The explicit return action restores the previously accepted builtin month; ordinary builtinMapBtn follow-now behavior stays unchanged.

Implementation boundary: add an explicit exact-date/scoped assembly path beside the monthly builtin loader, never a fallback in selectBuiltinCountries; compose the view through existing read-only document admission; preserve the original builtin-clock state in its canonical owner; add date/status notice and explicit return UI. No source validity, coordinate, lifetime, daily world cursor, editing or package writer changes are needed. A true daily world timeline would alter cursor and physical-resource contracts and is not the minimal choice.

A second, larger alternative is a catalog browser and independent source-reference overlay that stays visible while monthly world navigation continues. That needs new layer/picking/context state and clear mixed-date presentation. The explicit reference view is the smaller proposal because it avoids presenting different dates as one historical baseline.

This is a concrete product-path proposal, not an implementation or approval claim. No product code has been edited yet. Required actual-screen checks remain pending: source date/status visibility, repeated reference selections, return to the original month, previous/next months after return, invalid/cancelled/stale reads, and modern baseline preservation. No actual-screen usability verification is claimed at this checkpoint.
