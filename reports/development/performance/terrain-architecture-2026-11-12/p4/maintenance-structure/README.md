# 후보 구조의 유지보수·자원 책임 비교

앱 `9d2b4008c`의 실험 코드와 기존 구현을 읽은 정성적 분석이다. 코드 줄 수는 책임의 대략적 범위를 보여줄 뿐 품질·난이도 점수가 아니다. 성능과 실제 GPU 메모리는 별도 실측을 따른다.

| 후보 | 새로 유지할 책임 | 현재 확인된 제약 |
|---|---|---|
| A0 | 기존 가시 타일 선택, fetch·디코딩·GPU 업로드, 타일별 격자 및 Canvas 색상 캐시 | 이미 제품에 존재한다. 현행 색상 보간과 Q1/PCHIP 기준은 동등하지 않다. |
| A1 | Q1 복호화 후 보간과 공통 PCHIP 셰이더 (`a1-shader.mjs` 80줄) | 실험 자료는 LOD5의 제한 구역이고 Canvas 실화면 동등성은 미검증이다. 기존 타일별 자원 관리를 사용한다. |
| B512 | 타일 크기·매니페스트·gutter 관리 | 크기만 변경한 후보는 기존과 같은 그리기다. 작은 타일은 파일 수와 가시 타일 수가 늘 수 있다. |
| B 묶음 | 기존 텍스처 외 3×3 atlas, 타일별 주소·격자별 인스턴스·WebGL 상태 복원·GPU 자원 재생성 (`viewer-tile-batch.mjs` 84줄) | 최대 atlas 예산 64MiB는 실험 설정이다. 단일 화면에서 두 atlas 19,022,112바이트가 기존 타일 캐시에 추가됐다. 512 LOD5만 지원하고 다른 경우는 기존 경로이며 컨텍스트 손실·실 GPU는 미검증이다. |
| C | 검증 가능한 범위 요청, 32MiB 구간 LRU와 취소 공유, COG 블록 디코딩, 32MiB PNG 캐시 및 이미지 변환 (`verified-cog-reader.mjs` 81줄, `viewer-cog-tiles.mjs` 58줄, 외부 geotiff 디코더) | 두 캐시 상한은 각각 별도이고 브라우저 디코딩·GPU 자원은 포함하지 않는다. 호스트의 206/CORS·바이트 무결성·파일 제한이 필요하다. 실제 네트워크 단일 지역에서는 부분 읽기 초과 전송이 관찰됐다. |
| D | 화면별 역투영, atlas 갱신, 벡터 스텐실과 GL 상태·화면 외 지역 처리 (`viewer-screen-space.mjs` 119줄) | 시제품은 2,050×2,050 RGBA atlas 하나당 16,810,000바이트를 기존 텍스처와 별도로 사용한다. 경계 화질과 해안·극지·실 GPU·Canvas는 미검증이다. |
| B-archive | PMTiles 디렉터리·범위 무결성·사용자 지정 EPSG:4326 격자 주소 변환 | 일반 Web Mercator 클라이언트와 지리적 주소가 다르다. 실제 기본 CDN에서 잘못된 범위를 관측했으며 검증 클라이언트가 거부했다. |
| E | C와 D의 데이터·렌더링 책임을 함께 유지 | 두 후보의 독립 이득이 입증되지 않아 구현하지 않았다. |

코드 줄 수는 공통 P7·기존 제품 코드·외부 의존성을 제외했으며, 코드 생명주기·네트워크 운영 및 추후 완성에 필요한 구현량을 수량화하지 않는다. 따라서 이 표만으로 가중 점수나 최종 채택을 결정하지 않는다.
